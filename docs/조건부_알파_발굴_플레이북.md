# 조건부 알파 발굴 플레이북

> "이 조건에 맞는 알파를 오늘까지 하나 찾아라" 가 상시 요구다(Power Pool 주간 테마,
> 대회, 캠페인). 2026-07-21 에 1시간 만에 찾아낸 절차를 코드로 굳힌 결과물의 사용법과,
> 그때 실측으로 알아낸 것들을 남긴다.

## 1. 조건 걸기 — 이게 전부다

```bash
# 필터 문법 (Power Pool 캘린더에 붙는 형태 그대로)
python3.12 scripts/constraint.py --set \
  "region=USA & delay=1 & universe=TOP1000 & \
   High Turnover returns ratio test PASS & datasets not in ['pv1']"

# 자연어도 된다
python3.12 scripts/constraint.py --set "USA 딜레이1 TOP1000에서 pv1 제외하고 고회전 수익보존 통과하는 알파"

python3.12 scripts/constraint.py            # 현재 조건 보기
python3.12 scripts/constraint.py --check "…" # 저장 없이 파싱만 확인
python3.12 scripts/constraint.py --clear     # 해제
```

**재시작 불필요.** 워커가 라운드마다 `data/run_config.json` 을 새로 읽는다.

조건을 걸면 GA 가 도는 내내 **조건 밖 알파를 애초에 만들지 않는다** — region/delay/
universe 를 강제하고, 허용 중립화만 쓰고, 금지 데이터셋 필드를 팔레트에서 뺀다.
사후 필터링보다 훨씬 싸다(시뮬 한 건이 곧 일일 쿼터 5000 중 하나다).

### 조건이 실제로 막는 것들

| 층 | 무엇을 하나 |
|---|---|
| `settings()` | region·delay 강제 |
| `_apply_constraint()` | universe 덮어쓰기, 중립화를 허용 목록으로 스냅 |
| `_field_is_banned()` | 필드 + **합성필드 전개식**까지 검사 (`syn_clv` → close/high/low) |
| `_gene_uses_banned()` | `trade_when`·`regime`·`group_by` 템플릿이 금지 필드를 쓰면 그 유전자를 끔 |
| `constraint_spec.compliant()` | 시뮬 후 WQB 가 준 **실제 datasets** 로 최종 검증 |

마지막 층이 안전망이다. 필드→데이터셋 매핑은 CSV 커버리지 한계로 불완전하니
(아래 참조) 사후 검증을 건너뛰면 안 된다.

## 2. 금지된 데이터셋의 개념을 대체하기 — 발굴의 핵심

`datasets not in ['pv1']` 은 실무적으로 **"가격·거래량 데이터 없이 알파를 만들라"** 다.
계정의 고Sharpe 레시피가 전부 `-ts_zscore(close,5)`(단독 Sharpe 1.62)에 기대고 있어서
그 주에 통째로 막혔다. 해법은 **그 개념을 다른 데이터셋에서 다시 찾는 것**이다.

```python
from server import datafield_palette as dfp
dfp.find_substitutes('close', excluded=['pv1'], delay='1')
# → opt6_vimtaxp (option6) "Stock price taken at the time of IV calculation"
```

이렇게 찾은 것들이 그날의 돌파구였다:

| 금지 필드 | 대체 | 데이터셋 | 실측 |
|---|---|---|---|
| `close` | `opt6_vimtaxp` | option6 (cov 98%, 사용 알파 9개) | 단독 Sharpe **2.18** |
| `volume` | `shrt36_totalvolume` | shortinterest36 | 비율 단독 Sharpe **1.84** |
| `volume` | `aggregate_executed_trade_share_count` | us_short_sale | 비율 단독 Sharpe **2.28** |
| `returns` | `opt6_kw1gnhcxpkts` | option6 | Sharpe 0.99 |

**교훈**: 커버리지가 높은데 `alphaCount` 가 낮은 필드가 노다지다. `opt6_vimtaxp` 는
계정 전체에서 알파 9개만 썼다 — 사실상 아무도 안 건드린 주가 데이터였다.

## 3. 조절 노브 — 무엇이 듣고 무엇이 안 듣나 (실측)

| 노브 | 효과 | 비고 |
|---|---|---|
| **neutralization = STATISTICAL** | Sharpe **+38%**, MDD 절반 | 동일 식 1.72 → 2.47. 가장 큰 레버 |
| **decay** | 회전율 조절 | 0→100.5%, 2→79.6%, 4→62.0%, 6→53.3%, 8→48.5% |
| truncation | **무효** | 0.05·0.08·0.12·0.15 결과가 소수점까지 동일 |
| 공매도 비율 결합 | Sharpe +0.1~0.2 | |
| 변동성·IV 항 추가 | **역효과** | 2.38 → 1.82 |
| neutralization = RAM | **신호를 지움** | 2.38 → 0.46 (가격반전을 통째로 중립화) |

회전율이 70% 캡을 넘으면 decay 를 올린다. Sharpe 는 내려가지만 마진(비용 내성)은 오른다.

## 4. HT 수익보존비율의 정체

`HT_HIGH_TURNOVER_RETURNS_RATIO` 는 **PnL 실현지평의 함수**다:

| 지평 | 비율 | 판정 |
|---|---|---|
| 1~6일 | 0.88~1.17 | PASS |
| 16~120일 | 0.11~0.43 | WARNING |

즉 회전율 자체보다 **신호가 얼마나 빨리 소멸하는가**가 결정한다. 1일 변화량(`ts_delta(x,1)`)
기반 신호는 거의 무조건 통과한다. 문서도 같은 말을 한다 — *"High turnover should be a
consequence of the idea, not the idea itself."*

## 5. 알아둘 함정

- **회전율 대역은 1~70%**. 넘으면 `HIGH_TURNOVER` FAIL 로 제출이 막힌다. 소셜/센티먼트
  1일 혁신 신호는 HT 비율은 쉽게 통과하지만 회전율이 100~170% 로 튀어 못 쓴다.
- **자기상관 0.7 초과라도 통과할 수 있다** — 상관된 기존 제출 알파보다 Sharpe 가
  **10% 이상 높으면** 된다(공식 문서). 같은 아이디어를 개량하는 경로가 열려 있다.
- **같은 계열끼리는 뭉친다.** 가격반전 계열 5개를 확보해도 하루 1건씩밖에 못 넣는다.
  계열이 다른 후보(공매도 단독·옵션 IV 등)를 같이 길러야 매일 제출할 수 있다.
- **단위(Unit) 검사**: `implied_volatility / historical_volatility + 0.000001` 처럼
  상수를 더하면 `Incompatible unit for input of "add"` 로 컴파일이 막힌다.
  같은 단위끼리 `divide(a, b)` 로 나누거나, 각 항을 `ts_zscore`/`rank` 로 감싼 뒤 결합한다.
- **단일 데이터셋 알파는 IS Ladder 를 건너뛴다** (2년 컷만). 게다가 Genius 타이브레이커가
  "알파당 연산자·필드는 적을수록 유리" 라 **단순식이 채점표에서 유리하다**.
- **필드→데이터셋 매핑에 구멍이 있다.** `/data-fields` 는 count 를 10000 으로 캡하고
  필드 id 알파벳순으로 주는데 D1 은 필드가 그보다 훨씬 많다. pv1 은 curated 목록으로
  메웠지만(`PV1_FIELDS`), 다른 데이터셋은 CSV 에 있는 만큼만 안다.
  → **시뮬 후 `compliant()` 로 실제 datasets 를 다시 검증하는 게 최종 안전망이다.**
