### 2. IS-ladder test가 어떻게 이루어지는지 설명하라

`Sharpe = √250 × IR ≈ 15.8 × IR`, `IR = avg(일간 PnL) / stdev(일간 PnL)`

**전체 IS 기간 Sharpe 가 FAIL_THRESHOLD 미만이면 즉시 실패.** 아니면 반복 진입:

```
N_YEARS = 2
반복:
  Sharpe[N_YEARS] < FAIL_THRESHOLD          → FAILED
  Sharpe[N_YEARS] > PASS_THRESHOLDS[N_YEARS] → PASSED
  그 사이면                                   → N_YEARS += 1 후 재검사
```

즉 **최근 2년부터 시작해 통과할 때까지 1년씩 늘려가며** 벤치마크와 비교한다.

| 기간 | D1 | D0 |
|---|---|---|
| FAIL_THRESHOLD | 1.59 | 2.69 |
| 2~5년 | 2.38 | 3.96 |
| 6년 | 2.22 | 3.64 |
| 7년 | 2.06 | 3.33 |
| 8년 | 1.90 | 3.17 |
| 9년 | 1.74 | 2.85 |
| 10년 | 1.59 | 2.69 |

**핵심 단서 3가지**
- `Sharpe[N_YEARS]` 는 IS 기간 중 **최근** N 년으로 계산한다.
- **회전율 30% 미만이면 PASS_THRESHOLDS 에 ×0.85** 를 곱한다. **FAIL_THRESHOLD 엔 곱하지 않는다.**
- 실제 제출 판정에서는 사다리가 **0.75× / 0.85× / 1.0× 세 단계**로 적용된다:
  0.75× 실패 → "Improve Sharpe" / 0.75× 통과·0.85× 실패·회전율>10% → "Improve Sharpe or
  reduce turnover" / 0.85× 통과·1.0× 실패·회전율>30%·상관>0.3 → "…or reduce correlation".

**승급 조건 — 2단계**

*1단계: 자격요건 3가지 전부 충족*
1. 분기당 최소 **시그널 제출 수** (Alpha + SuperAlpha)
2. 최소 **피라미드 수** — 피라미드 = (리전 × delay × 데이터셋 카테고리), 예: USA-D1-analyst.
   해당 조합에 **알파 3개 이상** 제출해야 "형성"으로 인정. 알파 하나가 여러 필드를 쓰면
   여러 피라미드에 동시 귀속된다.
3. 최소 **Combined Alpha Performance** (OS Sharpe). 대시보드 4개 지표 중 **최댓값**을 쓴다:
   ① 제출 알파 전체 ② 그중 WQ 선정분 ③ **Power Pool 알파** ④ Osmosis.
   4~6주마다 갱신되며, 분기 마지막 달 제출분은 계산 지연으로 다음 분기에 반영된다.

구체 수치는 매 분기 사전 공지되고 상위 등급일수록 높아진다.

*2단계: 정원 경쟁 — 여기가 실제 관문*

| | Gold | Expert | Master | Grand Master |
|---|---|---|---|---|
| 정원 비율 | 70% | 20% | 8% | **2%** |

문서 원문: **"자격요건은 순위가 아니라 문턱"** 이라 간신히 넘든 크게 넘든 동일하며
상대적으로 쉽다. Grand Master 문턱을 넘어도 Master 가 보장되지 않는다 —
문턱을 넘은 사람끼리 **타이브레이커 점수(각 지표 순위의 합)** 로 정원을 다툰다.

**타이브레이커 지표**
- 알파당 평균 고유 **연산자** 수 — 낮을수록 유리
- 알파당 평균 고유 **필드** 수 — 낮을수록 유리
- 총 고유 **연산자** 수 — 높을수록 유리
- 총 고유 **필드** 수 — 높을수록 유리
- **최대 시뮬레이션 연속 기록** (분기마다 리셋되지 않음)
- 커뮤니티: 포럼 좋아요 수(100자 이상 글/댓글만)
- 추천(Referral) 성공 건수

※ `ts_backfill`, `group_backfill` 은 고유 연산자 집계에서 제외된다.
※ 정원 비율은 **직전 분기에 제출한 컨설턴트**(일일 한도 4알파+1슈퍼알파의 4% 이상 사용)
   수를 모수로 계산한다.

강등되면 데이터셋·연산자 접근이 실제로 회수되고, **접근을 잃은 필드를 쓴 기존 알파는
재시뮬이 불가**하다(단 SuperAlpha 구성에는 계속 쓸 수 있다).

### 4. Python 알파와 FASTEXPRESSION 알파의 주요 차이를 서술하라

**FAST EXPRESSION** — BRAIN 엔진 전용 표현식 언어. 제공된 연산자 집합 안에서 조합하며,
엔진이 벡터화 실행한다. **단위(Unit) 검사가 강제**되어 서로 다른 단위를 더하면 컴파일
단계에서 막힌다. 다중 문장(`;`)과 변수 할당으로 중간 신호를 조립할 수 있다.

**PYTHON ALPHA** — `@alpha` 데코레이터를 붙인 함수를 작성한다. 실행 모델이 근본적으로 다르다:

- **엔진이 매 시점(time step)마다 알파 함수를 한 번씩 호출**한다. 각 데이터 필드는
  `lookback + 1` 행의 이력을 담고 있다(`SimulationSettings.lookback` 로 설정).
  `lookback=0` 이면 1행(오늘만), `lookback=5` 면 6행. **가장 최근 데이터가 마지막 행.**
- **데이터 배열은 읽기 전용**이다. 제자리 수정하면 `ValueError` 가 난다 — 반드시 `.copy()`.
- **정수형 필드는 NaN 을 담을 수 없어** 결측이 타입 최솟값(`np.iinfo(np.int32).min`
  = -2147483648)으로 표현된다. `float32` 로 캐스팅하고 그 sentinel 을 NaN 으로 바꿔야 한다.
- 플랫폼 UI 에서는 Settings 의 LANGUAGE 드롭다운을 Python 으로 바꿔 그대로 시뮬·제출할 수
  있으며, **설정 파라미터가 Fast Expression 과 조금 다르다**.
- 알파 함수에서 직접 쓰지 않는 패키지는 import 하면 안 된다(UI 시뮬 시 제거 필요).

**두 가지 실행 경로가 있다 (Python 전용)**

| | BrainLabs 시뮬 | 실제(Actual) 시뮬 |
|---|---|---|
| 속도 | 빠름(로컬·캐시 데이터) | 느림(원격 API + 폴링) |
| 정확도 | 근사 | 정확 |
| 용도 | 개발·디버깅·파라미터 스윕 | 최종 검증·제출 |
| 파이프라인 | `generate_alpha_matrix` → `generate_alpha_positions` → `generate_alpha_stats` | 백엔드가 decay·중립화·pasteurization·truncation·포지션 변화 한도까지 전부 적용 |

BrainLabs 는 로컬 실행이라 **PnL 이 실제 환경과 조금 다를 수 있다**. `BrainCache` 로
데이터 조회를 캐싱하되, region·delay·기간을 바꾸면 새로 만들어야 한다.

**정리**: 신호가 횡단면·시계열 연산 조합으로 표현되면 FAST EXPRESSION 이 유리하다
(속도 = 탐색량 = 발굴 확률, 게다가 단위 검사가 실수를 잡아준다). Python 은 반복문·
상태 기반 로직·머신러닝 등 표현식으로 불가능한 구조가 필요할 때 쓴다.

### 5. multi-simulation, concurrent_simulation의 실행 방식을 서술하라

**⚠ 둘은 다른 축이고, 흔한 오해와 달리 곱셈으로 병렬성이 늘지 않는다.**

**Concurrent Simulation** = 동시에 점유 가능한 시뮬레이션 **슬롯 수**.
컨설턴트는 **8개**. 각 시뮬을 `POST /simulations` 로 보내면 응답 헤더 `Location` 에
progress URL 이 오고, 각각 독립적으로 폴링한다. 슬롯이 차면 다음 POST 는
**429 `CONCURRENT_SIMULATION_LIMIT_EXCEEDED`** 를 받는다.
`[실측]` 오늘 헌터가 8슬롯을 채운 상태에서 CHN 시뮬을 띄우려다 실제로 이 429 를 맞았다.

**Multi-Simulation** = 한 번의 실행에 **여러 알파를 묶는** 기능.
- 컨설턴트는 **최대 8개의 Multi-Simulation 을 동시 실행**할 수 있다.
- **각 Multi-Simulation 은 알파 10개까지 담을 수 있고, 그 10개는 순차(sequentially) 실행된다.**
- 10개는 연산자·데이터필드·설정이 서로 달라도 되지만, **Region 과 Delay 는 같아야 한다.**

따라서 실제 동시 처리량은 여전히 **8개**이며, Multi-Simulation 의 이득은 병렬성이 아니라
**요청·큐 오버헤드 절감과 변형 실험의 편의**다. 알파 아이디어 하나의 여러 변형을
한 묶음으로 돌릴 때 가장 유용하다.

**일일 시뮬 한도 (`Understanding simulation limits`)**
- **성공한 모든 시뮬이 카운트**된다. Multi-Simulation 의 자식 시뮬도, 이미 존재하는 알파의
  재시뮬도 포함된다. **중복 알파도 차감에서 제외되지 않는다.**
- 같은 알파를 다른 날 다시 시뮬하면 쿼터는 소모되지만 Alphas 페이지의 "Today" 에는
  안 보인다(최초 시뮬 날짜에만 나타남) — 추적 시 함정.
- API 응답 헤더로 확인한다: `X-Ratelimit-Limit`(일일 총량) · `X-Ratelimit-Remaining`(잔여) ·
  `X-Ratelimit-Reset`(리셋까지 초). 플랫폼 UI 는 1,000건 미만 남으면 경고를 띄운다.
- 한도 초과 시 **다음날(EST 기준)까지 추가 시뮬 불가**하므로, API 사용 시 잔여량을 보고
  스스로 멈췄다가 리셋 후 재개하는 로직을 넣으라고 문서가 명시한다.

## 부록 — 이번 발굴에서 확인된 것 (GenomicWQB 반영 대상)

- `option6` 에 **주가 필드가 그대로 있다** (`opt6_vimtaxp` = IV 산출 시점 기초자산 주가,
  커버리지 98%, 사용 알파 9개뿐). Power Pool 의 "PV1 금지" 를 우회하는 유일한 경로였다.
- `HT_HIGH_TURNOVER_RETURNS_RATIO` 는 **PnL 실현지평의 함수**다.
  지평 ≤ 7일이면 0.88~1.17 로 PASS, 16일 이상이면 0.11~0.43 으로 미달.
- **decay 가 회전율 레버**다. 동일 식에서 decay 0 → 100.5%, 2 → 79.6%, 4 → 62.0%,
  6 → 53.3%, 8 → 48.5%.
- **STATISTICAL 중립화가 결정적이다** — 동일 식에서 SUBINDUSTRY 1.72 → STATISTICAL **2.47**,
  MDD 는 절반 이하(4.35%). HT 하위분류 3종(AFTER_COST·INVESTABLE·LIQUID)도 함께 얻는다.
- **자기상관 0.7 초과라도 통과할 수 있다** — 상관된 기존 제출 알파보다 **Sharpe 가 10% 이상
  높으면** 된다. (제출된 `akEMEvk6` 이 자기상관 0.876 으로 통과한 실제 이유.)
- 타이브레이커가 "알파당 연산자·필드는 적게, 전체는 다양하게" 를 요구하므로
  `-ts_zscore(opt6_vimtaxp, 5)` 같은 **연산자 1개·필드 1개짜리 단순식(Sharpe 2.18)** 이
  Genius 채점표에서 최적에 가깝다.
